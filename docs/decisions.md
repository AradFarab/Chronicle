## استقلال از Frappe (تصمیم آراد، ۱۵ مهر ۱۴۰۵)

دلیل: Frappe بستر برنامه‌های دیگر هم هست و برای ما سنگین است (نصب، Desk، وابستگی به نسخه‌ها).

| موضوع | تصمیم |
| --- | --- |
| معماری | بک‌اند مستقل پایتون (FastAPI) روی PostgreSQL؛ بدون Frappe، Redis و MariaDB |
| دیتابیس | PostgreSQL با طرح تمیز و مستند (`docs/data-model.md`)؛ هر تغییر با مهاجرت Alembic؛ قیدها داخل خود دیتابیس |
| تاریخ | همچنان شمسی؛ نوع `jdate` در دیتابیس با بررسی شکل `1405/07/14`. جدول «روز تقویم» حذف می‌شود؛ روز هفته از jdatetime و تعطیلی از جدول تعطیلات |
| تقویم و تعطیلات | منبع رسمی time.ir؛ اپراتور آخر هر سال (یا هر وقت لازم شد) «به‌روزرسانی تقویم» را برای سال بعد می‌زند، پیش‌نمایش تغییرات را می‌بیند و تأیید می‌کند. داده آفلاین داخل برنامه برای وقتی که اینترنت نیست، با برچسب «پیش‌بینی». ورود فایل هم ممکن است |
| کتابخانه‌ها | jdatetime برای محاسبه تاریخ؛ کتابخانه rokh بررسی شد ولی تاریخ قمری را با تقویم عربستان (ام‌القری) حساب می‌کند که با تقویم رسمی ایران گاهی یک روز فرق دارد، پس منبع تعطیلات نیست |
| رابط کاربری | همه صفحه‌ها، از جمله تعریف کاربر، پرسنل، شیفت، الگو و تنظیمات، داخل همان PWA |
| حفظ می‌شود | موتور قانون کار، تقویم شمسی، آداپتور دستگاه، خروجی‌ها، PWA و همه قواعد CLAUDE.md |
| ترتیب کار | ۱) دیتابیس PostgreSQL ۲) تقویم ۳) فرم‌ها و فرایندها (درخواست و تأیید) ۴) بقیه |

### جزئیات فنی پیاده‌سازی (۱۵ مهر ۱۴۰۵)

| موضوع | تصمیم |
| --- | --- |
| کارهای پس‌زمینه | فرایند جدا `hozur worker`: هر چند ثانیه دستگاه‌هایی که وقت خواندنشان رسیده را می‌خواند، صف کارها (جدول `job`) را اجرا می‌کند و هر شب محاسبه دیروز و امروز، تخصیص مرخصی ماه قبل و بستن سال مرخصی را انجام می‌دهد. همه این کارها تکرارپذیرند، پس اگر سرور یک شب خاموش باشد شب بعد جبران می‌شود |
| محاسبه دوباره | هر تغییر (تردد جدید، تأیید درخواست، تعطیلی، شیفت، الگو، قواعد) یک کار «محاسبه دوباره» در صف می‌گذارد؛ ماه‌های بسته و روزهای آینده هرگز محاسبه نمی‌شوند؛ تغییر تنظیمات حداکثر یک سال به عقب را دوباره حساب می‌کند |
| هشدار غیبت | جدول اعلان جدا ندارد؛ فهرست کسانی که چند روز کاری پشت سر هم غیبت دارند هنگام نمایش از روی کارکرد روزانه حساب می‌شود (فقط هشدار، ماده ۲۷) |
| بستن ماه | فقط وقتی ماه تمام شده، درخواست در انتظار ندارد و محاسبه‌ای در صف نیست؛ بازکردن با دلیل و ثبت در تاریخچه |
| رمز ارتباطی دستگاه | رمزنگاری‌شده با کلید برگرفته از `HOZUR_SECRET_KEY`؛ در پاسخ API و تاریخچه تغییرات نمی‌آید |
| صفحه‌های تنظیمات | جدول‌های ساده (شعبه، واحد، سمت، پرسنل، شیفت، الگو، انتساب، قواعد، انواع مرخصی، فرایند تأیید) با یک توصیف واحد در سرور و PWA ساخته می‌شوند؛ تقویم، دوره‌ها، کاربران، دستگاه‌ها و گزارش‌ها صفحه اختصاصی دارند |
| نشانی برنامه | PWA در ریشه سایت (`/`) و API زیر `/api`؛ ورود با صفحه ورود خود برنامه |
| استقرار | یک ایمیج Docker برای وب و worker، به‌همراه PostgreSQL 17 در `docker/compose.yml` روی سرور خود شرکت |

## تغییر ساختار سازمان (تصمیم آراد، ۱۷ مهر ۱۴۰۵)

| موضوع | تصمیم |
| --- | --- |
| اپراتور | اپراتور و مدیر سیستم یکی هستند؛ فقط نقش «مدیر سیستم» (admin) وجود دارد. مدیرعامل و مدیر نقش جدا نیستند و از روی سمت‌ها مشخص می‌شوند |
| کارمند = کاربر | هر کارمند یک کاربر هم هست. هنگام تعریف کارمند، نام کاربری (پیش‌فرض: کد پرسنلی) و رمز عبور هم ثبت می‌شود. کارمند ترک‌کار یا معلق وارد برنامه نمی‌شود |
| کد تفصیلی | فیلد جدید «کد تفصیلی» برای هر کارمند (یکتا، اختیاری) |
| واحد | واحد فقط یک برچسب ساده است که به افراد می‌خورد تا گزارش‌گیری آسان شود؛ سلسله‌مراتب، مدیر و جانشین ندارد. هر نفر یک واحد |
| سمت | سمت‌ها جدا تعریف می‌شوند و درخت (زیرشاخه) دارند. هر سمت می‌تواند چند نفر داشته باشد و هر نفر چند سمت. سمت را می‌شود به فرد داد و از او گرفت (تاریخ شروع و پایان؛ سابقه می‌ماند). سمتِ «مدیرعامل» بالای درخت است |
| پرنت | پرنت هر نفر کسانی‌اند که نزدیک‌ترین سمتِ پرشدهٔ بالای سمت او را دارند. اگر سمت بالا خالی باشد، یک سطح بالاتر. مدیرعامل پرنت ندارد |
| سه فرایند تأیید | ۱) پرنت تأیید می‌کند. ۲) پرنت و بعد مدیرعامل (اگر پرنت خودِ مدیرعامل باشد فقط تأیید او). ۳) مستقیم مدیرعامل. درخواست خودِ مدیرعامل تأیید نمی‌خواهد. هر کدام از دارندگان سمتِ پرنت می‌توانند تأیید کنند |
| واگذاری تأیید | هر کس که زیردست دارد می‌تواند اختیار تأییدش را برای بازه‌ای به شخص دیگر واگذار کند؛ هم او و هم نماینده می‌توانند تأیید کنند و سابقه نشان می‌دهد چه کسی تأیید کرده |
| محل کار | «شعبه» حذف و به «محل کار» (مکان فیزیکی کار) تبدیل شد؛ استان محل کار تعطیلات استانی را مشخص می‌کند |
| ورود اکسلی | برای هر جایی که کاربر می‌تواند مورد جدید تعریف کند، نمونهٔ اکسل با همهٔ فیلدها و قالب‌ها (متن برای تاریخ و ساعت، لیست‌های کشویی) دانلود می‌شود و فایل پرشده با همان اعتبارسنجی فرم وارد می‌شود. ورود «همه یا هیچ» است و ردیف‌های اشتباه با شمارهٔ ردیف گزارش می‌شوند |
| شیفتِ شبانه | شیفت ۱۸ تا ۶ صبح روز بعد درست حساب می‌شود (ورود و خروج به روزِ شروع شیفت تعلق دارد؛ شب‌کاری ۲۲ تا ۶ جدا حساب می‌شود) و با آزمون پوشش داده شده است |
| چرخش دو هفته‌ای | الگوی «چرخشی» با چرخهٔ ۲۸ روزه (۱۴ روز صبح، ۱۴ روز شب) پشتیبانی می‌شود. برای اینکه دو گروه نگهبان یکی صبح و دیگری شب شروع کنند، هر انتساب «شروع از روزِ چندم چرخه» (`cycle_offset_days`) دارد |
| بیمه‌ای‌ها | ساخته نشد. درخواست «افرادی که فقط برایشان بیمه رد می‌شود و در گزارش معلوم نباشد کار نمی‌کنند» یعنی نشان‌دادن کار برای کسی که کار نمی‌کند؛ این در گزارش‌های حضور و بیمه جعل سابقه است و ساخته نمی‌شود. اگر نیاز واقعی چیز دیگری است (مثلاً فهرست بیمه جدا از حضور و غیاب) باید توضیح داده شود |

## ارتقای ورود اکسلی، الگوی کاری گرافیکی و پشتیبان‌گیری (درخواست آراد، ۱۹ مهر ۱۴۰۵)

| موضوع | تصمیم |
| --- | --- |
| ورود اکسلی آزاد | هر جا ورود اکسلی هست، کاربر اکسل یا CSV خودش را با هر ترتیب ستونی می‌اندازد. پنلی باز می‌شود که ستون‌های فایل را به فیلدها وصل می‌کند (پیشنهاد خودکار از روی عنوان ستون؛ یا یک مقدار ثابت برای همهٔ ردیف‌ها). برنامه ساعت‌ها («۹»، «9.30»، «۵ ب.ظ»، ساعت اکسل) و تاریخ‌ها («1405/7/1»، «14050701»، تاریخ واقعی اکسل که میلادی است و یک بار تبدیل می‌شود)، ارقام فارسی و حروف عربی (ي، ك) را استاندارد می‌کند. پیش از ذخیره همهٔ ردیف‌ها با همان اعتبارسنجی فرم بررسی و پیش‌نمایش می‌شوند (چه چیزی تغییر کرد، کدام ردیف خطا دارد). ورود همچنان «همه یا هیچ» است |
| استراحت | هر شیفت می‌تواند چند استراحت (ناهار، نماز، چای) داشته باشد و همه **بی‌حقوق** و خارج از ساعت کارند (ماده ۵۱) |
| بازهٔ مجاز اضافه‌کار | روی شیفت بازه‌هایی رسم می‌شود که فقط کارِ داخل آن‌ها می‌تواند اضافه‌کار شود، و همچنان درخواست و تأیید لازم دارد. کارِ بیرون از این بازه‌ها «کار بدون مجوز» با هشدار است. شیفت بدون بازه مثل قبل است |
| ارفاق ورود و خروج | تا حد ارفاق بخشیده می‌شود؛ بیشتر از آن **کل زمان** حساب می‌شود. مثال با ارفاق ۱۵ دقیقه و شیفت ۹ تا ۵: ورود ۹:۱۰ تأخیر ندارد، ورود ۹:۲۰ یعنی ۲۰ دقیقه تأخیر؛ خروج ۵:۱۰ اضافه‌کار ندارد، خروج ۵:۲۰ یعنی ۲۰ دقیقه کار اضافه (پیش‌تر فقط مازاد بر حد شمرده می‌شد) |
| تعریف گرافیکی | شیفت روی خط زمان و الگوی کاری در جدولی (ردیف: روزهای هفته یا روزهای چرخه، ستون: ساعت‌ها) با کشیدن نوار تعریف می‌شود: ساعت کار، استراحت، بازهٔ مجاز اضافه‌کار با رنگ‌های جدا |
| تخصیص گروهی | یک الگوی کاری را می‌شود یک‌جا به چند نفر داد (همه یا هیچ). انتساب جدیدتر از تاریخ شروعش بر قبلی‌ها مقدم است |
| مرتب‌سازی و فیلتر | همهٔ جدول‌ها مانند اکسل مرتب‌سازی و فیلتر ستونی دارند |
| درخواست پیشنهادی | پس از محاسبهٔ هر روز، برنامه درخواست پیشنهاد می‌دهد: کار اضافه در بازهٔ مجاز → اضافه‌کار (مثلاً ۱۷ تا ۱۹)، تأخیر یا تعجیل → مرخصی ساعتی، تردد ناقص → اصلاح تردد. کارمند خودش ارسال (رضایت ماده ۵۹) یا رد می‌کند؛ چیزی خودکار ثبت نمی‌شود و پیشنهادِ ردشده دوباره نمی‌آید. برای کار سخت و زیان‌آور و کارگر نوجوان اضافه‌کار پیشنهاد نمی‌شود (مواد ۶۱ و ۸۴) |
| پشتیبان‌گیری | در تنظیمات: پشتیبان فوری، پشتیبان خودکار شبانه در ساعت دلخواه با نگه‌داشتن N نسخهٔ آخر، دانلود و حذف. هر پشتیبان یک zip است (کل پایگاه داده با pg_dump و فایل‌های بارگذاری‌شده) و روی سرور شرکت می‌ماند. بازگردانی همه‌چیز را جایگزین می‌کند، پس فقط با فرمان `hozur backup restore` روی سرور انجام می‌شود |

| نام | نام برنامه **Chronicle** (کرونیکل) است و بیشتر نام انگلیسی به کار می‌رود: عنوان برنامه، آیکون و صفحهٔ ورود «Chronicle» و نشانه «C» است. «حضور و غیاب» توصیف کار برنامه است و می‌ماند |

| پایگاه داده | نام پایگاه داده و کاربر PostgreSQL همان `hozur` ماند تا داده‌های نصب‌های موجود بدون انتقال حفظ شوند |

## ماژول پیامک و فیش حقوقی (درخواست کاربر پروژه، ۲۷ مهر ۱۴۰۵)

برنامهٔ مستقل «fish» (Flask) به یک ماژول Chronicle تبدیل شد و برای ارسال پیامک یک بخش عمومی «پیامک» در پنل مدیر سیستم ساخته شد تا بعداً برای هر پیامک دیگری هم به کار رود. معماری پیامک از سند انتقال «SMS-HANDOFF-attendance» (پروژهٔ کلینیک) گرفته شده و با پشتهٔ Chronicle (FastAPI، جدول `job`، بدون Celery) تطبیق داده شد. حقوق و دستمزد همچنان خارج از دامنه است: Chronicle هیچ مبلغی حساب نمی‌کند؛ نرم‌افزار مالی PDF فیش‌ها را می‌دهد و Chronicle فقط آن را به صاحبش می‌رساند.

### پیامک

| موضوع | تصمیم |
| --- | --- |
| دروازهٔ ارسال | هسته فقط `dispatch(event, to, context)` را صدا می‌زند؛ جزئیات پنل پشت یک درایور است. ارسال همیشه در worker انجام می‌شود، هرگز داخل درخواست وب |
| درایور | با کد ثبت‌شده انتخاب می‌شود (نه مسیر ماژول از دیتابیس). فرم تنظیمات از `config_schema` خود درایور ساخته می‌شود. سه سبک: متن کامل (`bulk`)، پترن با متغیر نام‌دار (sms.ir)، پترن با متغیر ترتیبی. نسخهٔ اول: sms.ir و mock؛ کاوه‌نگار و ملی‌پیامک بعداً با یک فایل |
| پنل اصلی و پشتیبان | حداکثر یک پنل فعال اصلی و یک پشتیبان (قید در دیتابیس). رد قطعی پنل اصلی به پشتیبان می‌رود |
| رویداد و قالب | رویدادها در کد ثابت‌اند و هنگام نصب همگام می‌شوند. قالب فقط «روش ارسال» است، نه محرک؛ محرک در کد کسب‌وکار است. قالب هنگام ذخیره اعتبارسنجی می‌شود (نه هنگام ارسال) |
| پترن نام‌دار | نام متغیر در `param_map` باید دقیقاً نام متغیر متن تأییدشدهٔ پنل باشد؛ sms.ir برای نام ناشناخته خطا نمی‌دهد و پیام را با `#NAME#` خام می‌فرستد. پیش‌نمایش دقیقاً همان چیزی را نشان می‌دهد که به API می‌رود |
| لینک | پنل لینک کامل را به‌عنوان پارامتر نمی‌پذیرد و پارامتر کوتاه است؛ دامنه در متن تأییدشده ثابت است. پس هر `x_path` یک لینک کوتاه `l/<کد ۸ نویسه>` می‌شود (۱۴ روز، فقط مسیر ذخیره می‌شود، نه دامنه) و `/l/<کد>` به صفحهٔ اصلی می‌رود |
| ارسال تکراری | پیش از تماس شبکه، پیام با یک `UPDATE` شرطی (`queued → sending`) تصاحب می‌شود. نتیجهٔ نامعلوم (پاسخ نیامد یا خطای غیرمنتظره) `unknown` می‌شود و هرگز خودکار تکرار نمی‌شود و به پنل پشتیبان هم نمی‌رود؛ مدیر از گزارش پنل تصمیم می‌گیرد. هر رویداد برای هر موجودیت (`entity_key`) فقط یک‌بار ثبت می‌شود (قید دیتابیس) |
| پنجرهٔ ارسال | پیش‌فرض ۹ تا ۲۱؛ بیرون از آن تا صبح بعد نگه داشته می‌شود. رمز یک‌بارمصرف از ویژگی رویداد (`bypasses_send_window`) مستثنی است، نه از مقایسهٔ کد |
| لغو اشتراک | به‌ازای شماره و دسته (خدماتی یا تبلیغاتی)؛ پیام تبلیغاتی به شمارهٔ لغوکننده `skipped` ثبت می‌شود و جابی ندارد |
| کلید پنل | با کلید رمزنگاری Chronicle (`CHRONICLE_SECRET_KEY`) رمز می‌شود و در رکورد، لاگ و API ماسک است. (سند انتقال کلید جدا پیشنهاد می‌کرد؛ Chronicle همان سازوکار کلید دستگاه‌ها را نگه می‌دارد.) |
| محرک‌ها | بدون قالب فعال هیچ پیامی نمی‌رود. وصل‌شده‌ها: درخواست مرخصی برای تأییدکننده، تأیید/رد مرخصی، نتیجهٔ اصلاح تردد، یادآوری شیفت (عصر روز قبل)، ورود ثبت‌نشده، خروج ثبت‌نشده، تأخیر و غیبت برای مدیر، خلاصهٔ ماهانه، تبریک تولد، فیش حقوقی. `otp` و `user_invite` و `password_reset` تعریف شده‌اند ولی محرکی ندارند، چون Chronicle این جریان‌ها را ندارد |
| آزمون با حساب واقعی | شکل درخواست‌های sms.ir (`send/verify`، `send/bulk`، `credit`) از سند انتقال گرفته شده که با حساب واقعی آزموده شده بود؛ در Chronicle هنوز با حساب واقعی اجرا نشده است. پیش از استفاده یک پترن با دست‌کم سه متغیر بسازید و متن رسیده را بخوانید |

### فیش حقوقی

| موضوع | تصمیم |
| --- | --- |
| ورودی | PDF چندصفحه‌ای خروجی نرم‌افزار مالی؛ هر صفحه با «کد پرسنلی» چاپ‌شده روی آن (لایهٔ متنی، بدون OCR) به یک کارمند تطبیق داده می‌شود. کد پرسنلی با عدد انتهای کد کارمند مقایسه می‌شود (۴۲ ≡ EMP042) |
| پرسنل | اکسل پرسنل لازم نیست: کارمندان خود Chronicle‌اند (موبایل و کد ملی از پروندهٔ کارمند) |
| امنیت لینک | توکن تصادفی (فقط SHA-256 آن ذخیره می‌شود)، انقضا (۱۴ روز)، سقف بازدید (۵)، قفل پس از پاسخ اشتباه (۵)، عامل دوم ۴ رقم آخر کد ملی، واترمارک نام و زمان روی هر فیش، بدون کش. کد ملی چاپ‌شده روی فیش باید دقیقاً کد ملی کارمند باشد، وگرنه لینک ساخته نمی‌شود |
| ارسال | ادمین پیش‌نمایش (تعداد، کنارگذاشته‌ها و دلیل، نخستین پیام دقیقاً مثل ارسال) را می‌بیند و خودش «ارسال» را می‌زند. ارسال دوباره لینک قبلی را باطل می‌کند. پیامِ در راه دوباره صف نمی‌شود؛ پیامک ناموفق با «افراد بدون لینک سالم» دوباره می‌رود؛ پیامِ نامعلوم فقط با انتخاب «همه» |
| داده قبلی fish | منتقل نشد؛ از صفر شروع می‌شود |
